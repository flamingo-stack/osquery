Brief description of the file's purpose: Declares the decorator system for osquery, which allows dynamic key-value metadata to be attached to log items at configurable execution points.

## Key Components

- **`DecorationPoint` (enum)** — Defines when decorators execute:
  - `DECORATE_LOAD` — runs once on config load
  - `DECORATE_ALWAYS` — runs on every log event
  - `DECORATE_INTERVAL` — runs at scheduled intervals

- **`kDecorationPointKeys`** — A constant map linking each `DecorationPoint` to its corresponding configuration key string.

- **`runDecorators()`** — Iterates all registered decorators for a given `DecorationPoint`, optionally filtered by time (for interval-based decorators) or a specific config source.

- **`getDecorations()`** — Retrieves the current accumulated decoration results as a `map<string, string>` of column names to values. Called before log dispatch.

- **`clearDecorations()`** — Removes stored decorations for a specific config source, typically invoked when that source updates.

## Usage Example

```c
#include <osquery/logger/plugins/decorators.h>

// Run all "always" decorators before logging
osquery::runDecorators(osquery::DECORATE_ALWAYS);

// Run interval decorators with current epoch time
osquery::runDecorators(osquery::DECORATE_INTERVAL, currentTime);

// Retrieve decoration key-value pairs to attach to a log entry
std::map<std::string, std::string> decorations;
osquery::getDecorations(decorations);
// decorations now contains metadata like {"hostname": "myhost", "user": "admin"}

// Clear decorations for a config source that just reloaded
osquery::clearDecorations("filesystem");
```

## Notes

- Decorations are applied automatically by logging APIs (`logString`, `logSnapshot`, etc.) before downstream dispatch.
- Source-level isolation via `clearDecorations()` ensures stale metadata does not persist across config reloads.
